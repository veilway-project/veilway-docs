API کنترل راهی است که پنل، یک اسکریپت یا کلاینت TypeScript با آن گره در حال اجرا را می‌خوانند و تغییر می‌دهند. این API از نوع HTTP/1.1 با بدنهٔ JSON است و `veilway run` آن را روی یک سوکت یونیکس ارائه می‌دهد. همهٔ مسیرها زیر `/v1` هستند و `GET /v1/openapi.json` سند OpenAPI 3.1 همه آن‌ها را برمی‌گرداند.

هر که بتواند سوکت را باز کند مدیر گره است. او می‌تواند پیکربندی در حال اجرا را بخواند (بدون رازهایش)، آن را عوض کند و همهٔ کاربران را زیر نظر بگیرد. توکن، TLS و شنونده TCP وجود ندارد: دسترسی فقط با مجوزهای فایل سوکت تعیین می‌شود.

API فقط روی یونیکس ساخته می‌شود. روی سیستم‌های دیگر `veilway run` پرچم `--api` و `--no-api` ندارد و گره بدون API اجرا می‌شود.

## سوکت

| | |
|---|---|
| مسیر | `--api <path>`، پیش‌فرض `veilway.sock` کنار فایل پیکربندی |
| حالت (mode) | `600`: کاربری که گره با آن اجرا می‌شود، و root |
| خاموش کردن | `--no-api` |

- **حالت از همان ابتدا.** سوکت داخل یک پوشهٔ تازه با حالت `700` ساخته می‌شود، همان‌جا حالت `600` می‌گیرد و بعد به مسیرش لینک می‌شود. پس در هیچ لحظه‌ای، با هر umask، برای دیگران باز نیست.
- **سوکت کهنه.** فایل سوکتی که کسی پشتش پاسخ نمی‌دهد و گره‌ای که درست خاموش نشده به‌جا گذاشته، جایگزین می‌شود و این در لاگ با سطح info ثبت می‌شود.
- **سوکت زنده.** اگر پردازش دیگری روی آن مسیر پاسخ بدهد، گره راه نمی‌افتد و دلیلش را می‌گوید.
- **هر چیز دیگر.** فایلی در آن مسیر که سوکت نیست هرگز پاک نمی‌شود. گره راه نمی‌افتد و مسیر را نام می‌برد.
- **شکست در شروع.** سوکتی که ساخته نشود گره را متوقف می‌کند. گره‌ای که قرار بوده مدیریت شود جایی اجرا نمی‌شود که کسی به آن دسترسی ندارد.
- **خاموشی.** API پیش از موتور متوقف می‌شود و فایل سوکت پاک می‌شود. سوکتی که در این میان گره دیگری مال خود کرده دست‌نخورده می‌ماند.

```
curl --unix-socket /srv/veilway/veilway.sock http://veilway/v1/status
```

روی سوکت یونیکس نام میزبان در URL هرگز جستجو نمی‌شود، پس هر نامی کار می‌کند.

## درخواست‌ها و پاسخ‌ها

- همهٔ بدنه‌ها JSON هستند. درخواستی که بدنه دارد باید با `Content-Type: application/json` فرستاده شود.
- هر پاسخی که موفقیت نیست این شکل را دارد، با وضعیتی که به آن بخورد:

```json
{"error": {"code": "stale_revision", "message": "The running config is not the one If-Match names. Read it again and apply the change to what runs now.", "details": [{"path": "revision", "message": "0f1e2d3c..."}]}}
```

| فیلد | معنی |
|---|---|
| `code` | نام snake_case پایدار، برای برنامه‌ها. |
| `message` | یک جملهٔ ساده، برای آدم‌ها. |
| `details` | فهرستی از `{"path", "message"}`. برای پیکربندی ردشده، هر خطا با مسیر فیلدش. اگر چیزی برای افزودن نباشد خالی است. |

هیچ پاسخ، رویداد یا خط لاگ API مقدار یک راز (`private_key`، `preshared_key`، `transport_keys`، `transport_secrets`، `username`، `password`) را نشان نمی‌دهد، فقط مسیرها را. یک مورد `details` هرگز مقداری از سند را ندارد.

### کدهای خطا

| وضعیت | `code` | چه زمانی |
|---|---|---|
| 400 | `bad_request` | بدنه تا انتها خوانده نشد. |
| 400 | `bad_json` | بدنه یک سند JSON نیست. |
| 404 | `not_found` | چنین مسیری وجود ندارد. |
| 404 | `user_not_found` | `GET /v1/users/{name}` یا ریست مصرف برای نامی که پیکربندی در حال اجرا ندارد. |
| 405 | `method_not_allowed` | مسیر این متد را نمی‌پذیرد. |
| 408 | `request_timeout` | درخواست در 30 ثانیه تمام نشد. برای apply و ریست مصرف پایین‌تر را ببینید. |
| 409 | `stale_revision` | `If-Match` ریویژنِ در حال اجرا را نشان نمی‌دهد. |
| 409 | `replay_absent` | ریست حافظهٔ replay روی گره‌ای که حافظه‌ای ندارد، چون هیچ ترنسپورت مبهم‌سازی‌شده‌ای اجرا نکرده است. چیزی تغییر نکرد. |
| 409 | `replay_busy` | ریست حافظهٔ replay وقتی ریست قبلی هنوز معلوم نیست روی دیسک نشسته باشد، یا وقتی گره در حال توقف است. چیزی تغییر نکرد. |
| 500 | `internal` | گره نتوانست پاسخش را بنویسد یا بررسی یک سند را تمام کند. |
| 500 | `replay_unwritten` | ریست حافظهٔ replay که فایلش نوشته نشد. بخش همان مسیر را ببینید. |
| 500 | `replay_writing` | ریست حافظهٔ replay که نوشتنش بعد از 10 ثانیه تمام نشده و هنوز ممکن است بنشیند. دوباره نخواهید. بخش همان مسیر را ببینید. |
| 413 | `body_too_large` | بدنه از 4 MiB بزرگ‌تر است. |
| 415 | `unsupported_media_type` | بدنه با `application/json` فرستاده نشد. |
| 422 | `config_invalid` | سند خطا دارد. `details` آن‌ها را فهرست می‌کند. چیزی تغییر نکرد. |
| 422 | `body_invalid` | بدنهٔ ریست مصرف JSON است ولی `{"totals": true}` یا `{"totals": false}` یا `{}` نیست. چیزی تغییر نکرد. |
| 422 | `config_not_prepared` | سند معتبر است ولی گره نتوانست آن را آماده کند (مثلاً شنونده‌ای که bind نمی‌شود). چیزی تغییر نکرد. |
| 428 | `precondition_required` | apply بدون هدر `If-Match`. |
| 503 | `too_many_connections` | گره همین حالا 64 اتصال را سرویس می‌دهد. |
| 503 | `too_many_streams` | گره همین حالا 32 جریان رویداد را سرویس می‌دهد. |

## مسیرها

| متد | مسیر | پاسخ |
|---|---|---|
| GET | `/v1/status` | نسخه، نسل و ریویژن پیکربندی، مدت کارکرد، شمارش‌ها |
| GET | `/v1/config` | پیکربندی در حال اجرا بدون رازها، و ریویژن آن |
| POST | `/v1/config/validate` | گزارش اعتبارسنجی یک سند |
| POST | `/v1/config/diff` | آنچه apply یک سند تغییر می‌دهد، و گزارش |
| PUT | `/v1/config` | سند را اعمال می‌کند |
| GET | `/v1/users` | همهٔ کاربران |
| GET | `/v1/users/{name}` | یک کاربر |
| POST | `/v1/users/{name}/usage/reset` | شمارش سهمیهٔ کاربر را از نو شروع می‌کند و کاربر را برمی‌گرداند |
| POST | `/v1/replay/reset` | حافظهٔ replay ترنسپورت‌های مبهم‌سازی‌شده را ریست می‌کند و آن را برمی‌گرداند |
| GET | `/v1/stats` | همهٔ شمارنده‌ها با نرخ زنده |
| GET | `/v1/sessions` | دستگاه‌های دارای نشست زنده |
| GET | `/v1/exits` | هر نقطهٔ خروج با سلامت upstream آن |
| GET | `/v1/inbounds` | هر ورودی با کلیدهای عمومی‌اش و رتبهٔ هر ترنسپورت |
| GET | `/v1/links` | هر لینک گرهِ فعال با وضعیت و شمارنده‌هایش |
| GET | `/v1/events` | Server-Sent Events |
| GET | `/v1/openapi.json` | سند OpenAPI 3.1 |

هر مسیر می‌تواند `408`، `503`، `404` و `405` را هم مثل جدول بالا برگرداند. جدول‌های زیر فقط آنچه مخصوص همان مسیر است را می‌آورند.

### `GET /v1/status`

| فیلد | نوع | معنی |
|---|---|---|
| `version` | string | نسخهٔ ساخت. |
| `generation` | integer | از 1 شروع می‌شود و با هر پیکربندی که اعمال شود یکی زیاد می‌شود. |
| `revision` | string | آنچه `If-Match` می‌گیرد. «ریویژن‌ها» را ببینید. |
| `uptime_secs` | integer | ثانیه‌های گذشته از راه‌افتادن موتور. |
| `inbounds`، `exits`، `users` | integer | پیکربندی در حال اجرا چندتا دارد. |
| `flows` | integer | فلوهای جدول فلو در همین لحظه. |
| `public_addresses` | فهرستی از string | آدرس‌های عمومی گره، همان‌طور که پیکربندی نام می‌برد: نام میزبان یا آدرس IP، بدون پورت. برای گرهی که آدرسی نام نبرده خالی است. |
| `certificates` | فهرست | گواهی‌های خودامضایی که گره برای ترنسپورت‌های `tls` با `"self_signed": true` ساخته، یکی برای هر آدرس شنود، به شکل `{"listen", "pin", "not_before", "not_after"}`. `pin` همان SHA-256 از SubjectPublicKeyInfo کلید است با base64 استاندارد، و وقتی گواهی دوباره ساخته شود همان می‌ماند. `not_before` و `not_after` ثانیهٔ یونیکس‌اند. برای گره‌ای که گواهی ندارد خالی است. |
| `addons` | object | `{"xray": {"installed", "release"}}`: آیا فایل اجرایی افزونهٔ Xray در پوشهٔ افزونه‌هاست، و گره کدام نسخهٔ Xray-core را اجرا می‌کند. |

### `GET /v1/config`

`{"revision", "generation", "document"}` را برمی‌گرداند. `document` پیکربندی در حال اجراست و هر راز در آن با نشانهٔ `"<redacted>"` عوض شده. ریویژن در هدر `ETag` هم فرستاده می‌شود.

### `POST /v1/config/validate`

بدنه: یک سند پیکربندی. چیزی تغییر نمی‌کند. پاسخ چه سند معتبر باشد چه نه `200` است:

| فیلد | معنی |
|---|---|
| `valid` | وقتی سند خطا نداشته باشد `true` است. |
| `report` | `errors` و `warnings` (فهرست‌هایی از `{"path", "message"}`)، `more_errors` و `more_warnings` (تعداد موارد بعد از 100 مورد اول هرکدام)، `shadow_cut_short` (بررسی قاعده‌هایی که قاعدهٔ قبلی پوششان می‌دهد در بودجه‌اش متوقف شد). |

بدنه‌ای که JSON است ولی پیکربندی معتبر نیست، سندی است که باید دربارهٔ آن گزارش داد و با `valid: false` پاسخ `200` می‌گیرد. بدنه‌ای که اصلاً JSON نیست `400 bad_json` است.

### `POST /v1/config/diff`

بدنه: یک سند پیکربندی. چیزی تغییر نمی‌کند. پاسخ `valid`، `report` مثل بالا و `diff` را دارد که برای سند نامعتبر `null` است. برخلاف `validate`، دنبال قاعده‌هایی که قاعدهٔ قبلی پوششان می‌دهد نمی‌گردد.

| فیلد `diff` | معنی |
|---|---|
| `inbounds`، `outbounds`، `exits`، `rules`، `users` | `{"added", "changed", "removed"}`، هرکدام فهرستی از تگ‌ها (برای کاربران نام‌ها). |
| `dns`، `log`، `routing_default`، `rules_reordered`، `notices`، `public_addresses`، `replay` | وقتی آن بخش تغییر کرده `true` است. برای `replay`، نرخ هر مبدأ بلافاصله اعمال می‌شود و اندازهٔ cache از شروع بعدی گره. |
| `inbound_changes` | برای هر ورودی تغییرکرده: `tag`، `restart` (تونل دوباره راه می‌افتد و نشست‌هایش قطع می‌شوند)، `transports_stopped` و `transports_started` (اندیس‌ها). ورودی‌ای که فقط `type`، `padding`، `transport_keys`، `upgrade_cookie` یا `upgrade_headers` آن عوض شده با `restart` برابر false و هر دو فهرست خالی می‌آید. افزودن ترنسپورت `udp-obfs` به ورودی‌ای که `mtu` نوشته‌شده ندارد `restart` است: `mtu` آن از 1420 به 1390 می‌رود. |
| `user_changes` | برای هر کاربر تغییرکرده: `name`، `devices_added`، `devices_removed`، `devices_readdressed`، `devices_rekeyed`، `devices_secrets_changed` (دستگاه‌ها با کلید عمومی) و `lost_access`. `devices_secrets_changed` دستگاه‌های مانده‌ای است که `transport_secrets` آن‌ها دیگر همان قبلی نیست؛ اتصال کنترلی که رازی را ثابت کرده که دیگر نیست بسته می‌شود، و نشست `udp-obfs` ای که با آن راز باز شده تمام می‌شود. |

outbound ای که `username` یا `password` آن در سند نوشته شده، و به‌جای نشانه نیامده، هر مقداری هم که باشد تغییرکرده فهرست می‌شود. وگرنه «تغییر نکرده» به کسی که رمزی را حدس زده می‌گفت حدسش درست بوده.

### `PUT /v1/config`

بدنه: یک سند پیکربندی. هدر: `If-Match` با ریویژنی که تغییر روی آن ساخته شده. سند را با همان reload ای که `SIGHUP` انجام می‌دهد اعمال می‌کند و بعد آن را در فایل پیکربندیِ شروع گره می‌نویسد.

| وضعیت | معنی |
|---|---|
| 200 | اعمال شد. |
| 409 | `If-Match` ریویژنِ در حال اجرا نیست. هدر `ETag` و تنها مورد `details` (با مسیر `revision`) ریویژنِ در حال اجرا را دارند. |
| 422 | `config_invalid` یا `config_not_prepared`. پیکربندی در حال اجرا دست‌نخورده است. |
| 428 | `If-Match` نیامده. |

پاسخ `200` این را دارد:

| فیلد | معنی |
|---|---|
| `revision`، `generation` | مال پیکربندی ای که الان اعمال است. ریویژن همان `ETag` هم هست. |
| `saved` | وقتی پیکربندی اعمال شده ولی نوشتنش در فایل پیکربندی نشده، `false` است، یعنی راه‌اندازی دوباره با پیکربندی قبلی برمی‌گردد. فرستادن دوبارهٔ همین سند نوشتن را دوباره امتحان می‌کند. |
| `save_error` | دلیل شکست نوشتن، به همان شکل که سیستم می‌گوید. وقتی `saved` برابر `true` است `null` است. |
| `diff` | آنچه apply اضافه، تغییر و حذف کرد، مثل `/v1/config/diff`. |
| `report` | هشدارهای پیکربندی ای که الان اعمال است. |

- **آنچه ذخیره می‌شود.** فایل همان بایت‌هایی نیست که فرستادید. گره سندی را که الان اجرا می‌کند می‌نویسد، با رازهای واقعی به‌جای هر نشانه، و با قالب‌بندی خودش. حالت `600`، فایل موقت در همان پوشه، `fsync`، rename و بعد `fsync` پوشه. اگر مسیر پیکربندی یک symbolic link باشد، فایلی که به آن اشاره می‌کند جایگزین می‌شود.
- **مهلت نوشتن.** نوشتنی که بعد از 10 ثانیه رها شده متوقف نمی‌شود، پس ممکن است فایل باز هم این پیکربندی را بگیرد. هرگز به پیکربندی قدیمی‌تر برنمی‌گردد.
- **مهلت زمانی.** 30 ثانیهٔ apply مربوط به خواندن و بررسی سند است. وقتی گره شروع به اعمال پیکربندی کرد، پاسخ هر قدر طول بکشد منتظرش می‌ماند و برای پیکربندی ای که بعد اعمال می‌شود هرگز `408` فرستاده نمی‌شود.
- **شکست.** سندی که رد شود یا آماده نشود همه‌چیز را همان‌طور که بود می‌گذارد. سندی که موتور در اعتبارسنجی یا آماده‌سازی رد کند با رویداد `config_refused` اعلام می‌شود. سندی که خود API هنگام خواندن نامعتبر بیابد با `422` پاسخ داده می‌شود و اعلام نمی‌شود.

## ریویژن‌ها و `If-Match`

ریویژن 64 رقم هگز است که بایت‌های پیکربندی در حال اجرا را نام می‌برد. هش کلیددار است و کلیدش را گره هنگام شروع تصادفی انتخاب می‌کند، پس کسی نمی‌تواند آن را از روی یک سند حساب کند و بعد از راه‌اندازی دوباره، همان پیکربندی ریویژن دیگری دارد.

apply هدر `If-Match` با ریویژنی که فراخواننده خوانده را لازم دارد. گیومه‌های `ETag` اختیاری‌اند. ریویژنی که ریویژنِ در حال اجرا نباشد، هر چه باشد، `409 stale_revision` است و پاسخ ریویژن فعلی را دارد تا فراخواننده پیکربندی را دوباره بخواند و تغییرش را دوباره انجام دهد. نبودن هدر `428 precondition_required` است. این بررسی پیش از اعمال سند دوباره با پیکربندی در حال اجرا انجام می‌شود.

```
curl --unix-socket veilway.sock -X PUT http://veilway/v1/config -H 'Content-Type: application/json' -H 'If-Match: "0f1e2d3c4b5a69788796a5b4c3d2e1f00f1e2d3c4b5a69788796a5b4c3d2e1f0"' --data @config.json
```

## ویرایش پیکربندی بدون دیدن رازها

`GET /v1/config` هرگز رازی را برنمی‌گرداند: `private_key`، `preshared_key`، `username` و `password` رشتهٔ `"<redacted>"` را دارند، و هر مورد از `transport_secrets` و از `transport_keys` یک ورودی نشانه‌ای دارد که همان را نام می‌برد: `"<redacted:1a2b3c4d>"` با هشت رقم hex. این رقم‌ها رازهای یک دستگاه، یا کلیدهای یک ورودی، را از هم جدا می‌کنند و چیزی دربارهٔ هیچ‌کدام نمی‌گویند. هر پردازهٔ گره آن‌ها را از نو می‌سازد، پس سندی که پیش از راه‌اندازی دوباره خوانده شده باید دوباره خوانده شود. پنل این سند را ویرایش می‌کند و همان‌طور به `validate`، `diff` یا `PUT /v1/config` برمی‌گرداند. در سندی که به گره فرستاده می‌شود، نشانه یعنی «مقدار در حال اجرای همان شیء را نگه دار»:

| فیلد | از کجا گرفته می‌شود |
|---|---|
| `private_key` ورودی | ورودی در حال اجرا با همان `tag` |
| `preshared_key` دستگاه | دستگاه در حال اجرا با همان `public_key` |
| یک مورد از `transport_secrets` دستگاه | رازی که این نشانه نام می‌برد، از دستگاه در حال اجرا با همان `public_key`، هر جای فهرست که باشد. موردی که حذف شود برداشته می‌شود: برای پایان چرخش، نشانهٔ راز قدیمی را بردارید و دیگری را نگه دارید. برای شروع آن، راز جدید را کامل کنار نشانهٔ رازی که می‌ماند بنویسید. |
| یک مورد از `transport_keys` ورودی | کلیدی که این نشانه نام می‌برد، از ورودی در حال اجرا با همان `tag`، هر جای فهرست که باشد. چرخش مثل رازهای دستگاه است: کلید جدید را کامل پیش از نشانهٔ کلید قدیمی بنویسید و آن نشانه را بعداً بردارید. |
| `username` و `password` خروجی | outbound از نوع `socks5` در حال اجرا با همان `tag` و همان `server` |

نشانه‌ای که چنین شیئی پیدا نکند در مسیر همان فیلد خطای اعتبارسنجی است. این شامل outbound ای هم می‌شود که `server` آن عوض شده: آن‌وقت سند باید username و password را صریح بنویسد. نشانه‌ای در `transport_secrets` که هیچ رازی از آن دستگاه را نام نبرد هم همین‌طور است، مثل `"<redacted>"` ساده یا نشانهٔ راز دستگاهی دیگر، و همین‌طور نشانه‌ای در `transport_keys` که هیچ کلیدی از آن ورودی را نام نبرد. `username` یا `password` برابر نشانه در فایل پیکربندیِ خوانده‌شده از دیسک هم خطای اعتبارسنجی است.

## کاربران، آمار، نشست‌ها، خروجی‌ها

### `GET /v1/users` و `GET /v1/users/{name}`

فهرست `{"users": [...]}` را برمی‌گرداند. مسیر تکی یک کاربر را برمی‌گرداند، یا `404 user_not_found`.

| فیلد | معنی |
|---|---|
| `name` | نام کاربر. |
| `enabled` | فقط وقتی پیکربندی `"enabled": false` بگوید `false` است. |
| `denied` | چرا کاربر همین حالا نمی‌تواند وصل شود: `disabled`، `expired` یا `quota`. برای کاربری که می‌تواند `null` است. |
| `expires_at` | مثل پیکربندی، یا `null`. |
| `quota_bytes`، `quota_period` | مثل پیکربندی، یا `null`. |
| `used_bytes` | بایت‌های هر دو جهت از `period_start`. |
| `period_start` | آخرین باری که شمارش از نو شروع شد، به ثانیهٔ یونیکس. برای کاربری که هرگز `quota_period` نداشته، یا هنگام آخرین ریست مصرفش نداشته، `0` است. |
| `dns_set` | تگ مجموعهٔ DNS که نام کاربر را آورده، و اگر چنین مجموعه‌ای نیست، مجموعه‌ای که نام یکی از گروه‌های او را آورده است. وقتی هیچ مجموعه‌ای این کار را نکرده `null` است: پرسمان‌های کاربر آن‌وقت به مجموعه‌ای می‌روند که نام ورودیِ محل آمدنشان را آورده، یا به `dns.servers`. |
| `traffic` | شمارنده‌های طول عمر: `up_bytes`، `up_packets`، `down_bytes`، `down_packets`. up یعنی از دستگاه به گره. |
| `devices` | برای هر دستگاه: `name`، `public_key`، `addresses`، `handshake_age_secs` (ثانیه‌های گذشته از ساخته‌شدن نشستش، بدون نشست `null`). |

کلید preshared هرگز در آن نیست.

### `POST /v1/users/{name}/usage/reset`

شمارش سهمیهٔ یک کاربر را از نو شروع می‌کند. دستور `veilway usage reset` همین مسیر را صدا می‌زند.

| | |
|---|---|
| بدنه | اختیاری. `{"totals": true}` یا `{"totals": false}`. بدون بدنه یعنی `false`. |
| `used_bytes` | `0` می‌شود. |
| `period_start` | آغاز دورهٔ سهمیه‌ای می‌شود که ساعت گره در آن است (00:00 UTC همان روز، دوشنبه یا روز اول ماه). برای کاربر بدون `quota_period` برابر `0`. |
| `traffic` | می‌ماند. با `"totals": true` چهار شمارندهٔ طول عمر هم `0` می‌شوند. |

| وضعیت | معنی |
|---|---|
| 200 | انجام شد. بدنه همان کاربر است، دقیقاً مثل پاسخ `GET /v1/users/{name}`. |
| 404 | `user_not_found`. چیزی تغییر نکرد. |
| 400، 413، 415 | `bad_json`، `body_too_large`، `unsupported_media_type`، برای بدنه‌ای که فرستاده شده و قابل استفاده نیست. چیزی تغییر نکرد. |
| 422 | `body_invalid`: بدنه JSON است ولی فیلدی جز `totals` دارد، یا `totals` برابر `true` یا `false` نیست. چیزی تغییر نکرد. |

- **عبور از سهمیه.** کاربری که به‌دلیل سهمیه قطع شده بود به‌محض فرستاده‌شدن پاسخ می‌تواند دوباره وصل شود. بارگذاری مجدد لازم نیست. کاربری که غیرفعال یا منقضی است همچنان رد می‌شود و `denied` در پاسخ همین را می‌گوید.
- **چیز دیگری عوض نمی‌شود.** نشست‌ها، جریان‌ها و پیکربندی همان می‌مانند. به کاربران دیگر دست زده نمی‌شود.
- **فایل state.** ریست پیش از پاسخ در فایل state نوشته می‌شود، نه در نوشتن 10 ثانیه‌ای بعدی. اگر آن نوشتن شکست بخورد یا بیش از 5 ثانیه طول بکشد، ریست همچنان اعمال شده است، شکست لاگ می‌شود و در `state_write_failures` شمرده می‌شود، و نوشتن دوباره تلاش می‌شود.
- **تکرار.** فرستادن دوبارهٔ همان درخواست بی‌خطر است. شمارش را دوباره `0` می‌کند و چیز دیگری را تغییر نمی‌دهد.
- **رویدادها.** یک رویداد `usage_reset` فرستاده می‌شود، و اگر کاربر از سهمیه گذشته بود پس از آن `user_restored`.
- **لاگ.** یک خط info با نام کاربر، شمارش پیش از ریست و اینکه مجموع‌ها صفر شدند یا نه.
- **مهلت.** 30 ثانیه فقط خواندن بدنه را می‌پوشاند. وقتی گره ریست را شروع کرد، پاسخ منتظرش می‌ماند و برای ریستی که بعد انجام می‌شود هرگز `408` فرستاده نمی‌شود.

```
curl --unix-socket veilway.sock -X POST http://veilway/v1/users/alice/usage/reset
curl --unix-socket veilway.sock -X POST http://veilway/v1/users/alice/usage/reset -H 'Content-Type: application/json' --data '{"totals": true}'
```

### `POST /v1/replay/reset`

حافظهٔ replay ترنسپورت‌های مبهم‌سازی‌شده را ریست می‌کند. دستور `veilway replay reset` همین مسیر را صدا می‌زند، و فقط برای یک حالت است: کف حافظهٔ replay از ساعت گره جلوتر است، چون ساعت جلو رفته بوده، و گره همهٔ دستگاه‌ها را رد می‌کند. [مرجع پیکربندی](../config/) این حالت را زیر `replay` توضیح می‌دهد.

درخواست بدنه ندارد. cache اثبات‌های پذیرفته‌شده خالی می‌شود، و کف و سقف برابر ساعت گره به‌اضافهٔ 60 ثانیه می‌شوند، حتی اگر از قبل کمتر باشد. فایل replay پیش از پاسخ و پیش از پذیرفتن اثبات بعدی نوشته می‌شود.

دو هزینه دارد:

- هر کلاینتی 60 ثانیه رد می‌شود.
- اثباتی که با زمانی بالاتر از کف تازه پذیرفته شده بود فراموش می‌شود. هر که آن را ضبط کرده باشد، وقتی ساعت به آن زمان برسد می‌تواند یک بار دیگر از آن استفاده کند.

| وضعیت | معنی |
|---|---|
| 200 | انجام شد و روی دیسک است. بدنه حافظهٔ replay بعد از ریست است، همان‌طور که `replay` در `/v1/stats` می‌دهد. |
| 409 | `replay_absent`: گره هیچ ترنسپورت مبهم‌سازی‌شده‌ای اجرا نکرده و حافظهٔ replay ندارد. `replay_busy`: ریست قبلی هنوز معلوم نیست روی دیسک باشد، یا گره در حال توقف است. چیزی تغییر نکرد. |
| 500 | `replay_unwritten`: فایل replay نوشته نشد، پس ریست ممکن است روی دیسک باشد یا نباشد. گره تا وقتی کف و سقف قبلی را دوباره ننوشته، که هر ثانیه یک بار تلاش می‌کند، هیچ اثباتی نمی‌پذیرد. بعد همان‌ها دوباره برقرارند و ریست باید دوباره خواسته شود. `replay_writing`: نوشتن بعد از 10 ثانیه تمام نشده است. ریست وقتی نوشتن تمام شود برقرار است، پس دوباره نخواهید: `GET /v1/stats` را بپرسید، که در آن `replay.resets` با نشستن ریست یکی بالا می‌رود و `replay.ready` تا وقتی گره هیچ اثباتی نمی‌پذیرد false است. |

- **چیز دیگری عوض نمی‌شود.** مصرف، سهمیه‌ها، نشست‌های باز، جریان‌ها و پیکربندی همان می‌مانند.
- **لاگ.** یک خط warn با کف و سقف قبل و بعد، و تعداد اثبات‌هایی که فراموش شدند.
- **مهلت.** پاسخ 10 ثانیه منتظر گره می‌ماند. نوشتنی که تا آن وقت تمام نشده باشد پاسخ `replay_writing` می‌گیرد، نه «دوباره بخواهید»: ریست دوم 60 ثانیهٔ دیگر هزینه دارد. برای ریستی که بعد انجام می‌شود هرگز `408` فرستاده نمی‌شود.

```
curl --unix-socket veilway.sock -X POST http://veilway/v1/replay/reset
```

### `GET /v1/stats`

یک عکس لحظه‌ای از همهٔ شمارنده‌ها، با نرخ به بایت بر ثانیه. گره شمارنده‌هایش را هر ثانیه نمونه می‌گیرد و نرخ برابر رشد بین قدیمی‌ترین و جدیدترین نمونه در 5 ثانیهٔ آخر است.

| فیلد | معنی |
|---|---|
| `window_secs` | ثانیه‌هایی که نرخ‌ها روی آن‌ها گرفته شد: وقتی گره این‌قدر کار کرده باشد 5، پیش از نمونهٔ دومش 0. |
| `users`، `inbounds`، `exits` | فهرست‌هایی از `{"name", "traffic", "up_bytes_per_sec", "down_bytes_per_sec"}`. `name` نام کاربر یا تگ است. نامی که در این بازه تازه است نرخ 0 دارد. |
| `outbounds` | برای هر outbound پیکربندی در حال اجرا یک مورد، به همان ترتیب: همان چهار فیلدِ یک خروجی، که `name` در آن تگ outbound است، به‌همراه `udp`، `udp_down_secs`، `udp_flips`، `latency_ms` و `measured_at`. `traffic` و دو نرخ، جمع خروجی‌هایی است که بک‌اندشان این outbound را نام می‌برد. outbound ای که هیچ خروجی از آن استفاده نمی‌کند با صفر فهرست می‌شود، و خروجی با بک‌اند `l3`، `block` یا `chain` هیچ outbound ای ندارد و زیر هیچ‌کدام شمرده نمی‌شود. گره برای outbound شمارندهٔ جدایی ندارد، پس این جمع هرچه را آن خروجی‌ها می‌شمارند در خود دارد، از جمله ترافیکی که سیاست `unsupported` یک خروجی با `"direct"` از کنار پروکسی فرستاده است. گره اینکه یک پروکسی UDP را رله می‌کند یا نه را برای هر خروجی جدا و از فلوهای همان خروجی می‌فهمد، پس این سه فیلد UDP چیزی است که خروجی‌های این outbound روی هم می‌دانند: تا وقتی آخرین تلاش یکی از آن‌ها رد شده باشد `udp` برابر `false` است و برای outbound ای که پروکسی SOCKS5 نیست `null`، `udp_down_secs` از تازه‌ترین رد می‌شمارد، و `udp_flips` جمع جابه‌جایی‌های خروجی‌هاست، پس یک تغییر پروکسی که دو خروجی متوجهش شوند دو بار شمرده می‌شود. وضعیت هر خروجی در `/v1/exits` است. `latency_ms` مدتی است که پروکسی برای پاسخ به greeting آخرین فلوی دایل‌کننده‌اش طول کشید، به میلی‌ثانیه، و `measured_at` زمان آن است، به ثانیهٔ یونیکس. برای outbound مستقیم و تا وقتی فلویی از پروکسی استفاده نکرده هر دو `null` هستند. reload آن‌ها را از نو شروع می‌کند. |
| `drops` | بسته‌هایی که از شروع حمل نشدند، به تفکیک نام دلیل. |
| `dns` | `answered`، `refused`، `failed`، `malformed`، `throttled`. |
| `flows` | فلوهای جدول فلو در همین لحظه. |
| `ws_stalled`، `ws_refused` | اتصال‌های WebSocket که ارتقا را تمام نکردند و رها شدند، و آن‌هایی که هنگام accept رد شدند. |
| `state_write_failures` | نوشتن‌های ناموفق فایل state مصرف از شروع. |
| `send_failed` | دیتاگرام‌هایی که گره برای دستگاهی ساخت و هیچ سوکتی نگرفت، روی همهٔ ترنسپورت‌های همهٔ ورودی‌ها. ورودی `veilway` هرگز تکه‌تکه نمی‌کند، پس بسته‌ای که از ظرفیت رابط میزبان بزرگ‌تر باشد اینجا شمرده می‌شود و فرستاده نمی‌شود، و هر دقیقه یک بار در سطح info لاگ می‌شود: وقتی بالا می‌رود `mtu` ورودی را کم کنید. |
| `control` | آنچه کانال کنترل ورودی‌های `veilway` از شروع انجام داده: اتصال‌های `accepted` و `authenticated`، اتصال‌های بسته‌شده به خاطر `auth_failed`، `malformed`، `timed_out` (گشایش بیش از 10 ثانیه طول کشید) و `replaced` (اتصال تازه‌تری از همان دستگاه جایش را گرفت)، درخواست‌هایی که پاسخ `rate_limited` گرفتند، `exits_selected`، `exits_refused` و `exits_dropped` (با بارگذاری مجدد)، `probe_runs`، `probes_confirmed`، `probes_sent`، `probes_refused`، `mtus_set`، `byes`، و `open` یعنی اتصال‌های احرازشدهٔ همین حالا. روی گره‌ای بدون ورودی `veilway` همه صفرند. |
| `udp_obfs` | آنچه ترنسپورت‌های `udp-obfs` از شروع انجام داده‌اند و آنچه همین حالا نگه می‌دارند. پایین را ببینید. روی گره‌ای بدون آن همه صفرند. |
| `stream` | آنچه شنونده‌های جریانیِ ترنسپورت‌های `tls`، و ترنسپورت‌های `ws` و `fronted` ورودی‌های `veilway`، از شروع انجام داده‌اند و آنچه همین حالا نگه می‌دارند. پایین را ببینید. روی گره‌ای بدون آن‌ها همه صفرند. |
| `replay` | حافظهٔ replay ترنسپورت‌های مبهم‌سازی‌شده. روی گره‌ای که هیچ‌کدام را اجرا نکرده `null`. پایین را ببینید. |

`udp_obfs`. هیچ شمارنده‌ای آدرس، تگ یا کلیدی را نام نمی‌برد، و دیتاگرامی که دور ریخته شده، به هر دلیلی، پاسخی نگرفته است:

| فیلد | معنی |
|---|---|
| `pending`، `sessions` | همین حالا: نشست‌هایی که بستهٔ آغازینشان پذیرفته شده و WireGuard هنوز روی آن‌ها احراز نشده، و نشست‌های برقرارشده. `sessions` نشست‌هایی را هم که نشست تازه‌تری از همان مبدأ جایشان را گرفته و 10 ثانیه خواندنی می‌مانند می‌شمارد. |
| `tags` | تگ‌های دوره‌ای در جدول‌های تگ در همین حالا: سه تا برای هر راز ترنسپورتِ هر دستگاهی که می‌تواند وصل شود. |
| `opened`، `established` | بسته‌های آغازینی که پذیرفته شدند، و نشست‌هایی که برقرار شدند. |
| `waited`، `spent` | بسته‌های آغازینی که تا نوشته شدن سقف بالاتر نگه داشته شدند و بعد دوباره به قاعدهٔ replay رفتند، و بسته‌های آغازینی که یک حد ردشان کرد و salt آن‌ها مصرف‌شده ثبت شد، تا کسی که یکی را دیده بعداً نتواند از آن استفاده کند. هر دستگاه برای این ثبت‌ها سهمی دارد: 16 تا یک‌جا و بعد یکی در ثانیه. بستهٔ ردشدهٔ بیش از آن ثبت نمی‌شود. |
| `short`، `unknown`، `open_failed` | دیتاگرام‌های کوتاه‌تر از یک بستهٔ داده. دیتاگرام‌هایی که بستهٔ نشستی در مبدأشان نیستند و تگشان در جدول تگ نیست: هر دیتاگرام یک غریبه اینجا شمرده می‌شود. و دیتاگرام‌هایی که تگشان در جدول هست و باز نمی‌شوند: فرستنده تگ این دوره را بدون راز دستگاه دارد، یا بسته در راه عوض شده است. |
| `sent` | بسته‌هایی که شنونده‌ها برای یک سوکت ساختند. هر کدام بستهٔ دادهٔ یک نشست برقرارشده است، پس گره‌ای که فقط غریبه‌ها با آن حرف می‌زنند اینجا 0 دارد. |
| `window`، `floor`، `seen`، `cache_full` | بسته‌های آغازین یک دستگاه که قاعدهٔ replay رد کرد: زمانی بیش از 60 ثانیه دور از ساعت گره، زمانی روی کف یا پایین‌تر، بسته‌ای که قبلاً پذیرفته شده، و هر بسته‌ای وقتی cache پر است. `window` ای که برای یک دستگاه بالا می‌رود نشانهٔ ساعت غلط روی آن دستگاه یا روی گره است. |
| `limit`، `no_replay` | بسته‌های آغازین با زمانی بالاتر از سقف نوشته‌شده که دور ریخته شدند، چون شنونده از پیش 64 بستهٔ دیگر نگه داشته بود یا هیچ نوشتنی ظرف 2 ثانیه تمام نشد، و آن‌هایی که وقتی آمدند که گره هیچ اثباتی نمی‌پذیرفت. |
| `source_devices`، `pool`، `pending_full`، `device_rate`، `source_rate` | بسته‌های آغازینی که یک حد ردشان کرد: مبدأ نشست 4 دستگاه دیگر را دارد، `limits.sessions` شنونده پر است، دستگاه 2 نشست معلق دارد، یا سهم دستگاه (16، بعد یکی در ثانیه) یا سهم مبدأ (`replay.per_source`) تمام شده است. |
| `handshakes`، `tunnel`، `unsendable` | آغاز handshake های WireGuard بیش از سهم یک نشست (3، بعد یکی در ثانیه)، دیتاگرام‌هایی درون یک نشست که WireGuard آن‌ها را بستهٔ دستگاهِ همان نشست ندانست، و بسته‌هایی که گره نتوانست بسازد. |
| `ended_deadline`، `ended_idle`، `ended_packets`، `ended_replaced`، `ended_displaced`، `ended_revoked` | نشست‌هایی که تمام شدند: بدون بستهٔ WireGuard تا 10 ثانیه بعد از بستهٔ آغازین، 180 ثانیه بدون فعالیت، 2^31 بستهٔ فرستاده‌شده، نشست تازه‌تری از همان مبدأ و دستگاه، نهمین نشست دستگاه، و دستگاه یا راز ترنسپورتی که پیکربندی دیگر ندارد. |
| `table_rebuilds`، `table_rebuilds_late`، `table_build_failures`، `tag_collisions` | چند بار جدول تگ برای دورهٔ تازه ساخته شد (هر 120 ثانیه برای هر ورودی)، چند بار این کار بیش از 10 ثانیه دیر شد، چند بار ساختن تمام نشد و جدول قبلی ماند، و تگ‌هایی که کنار گذاشته شدند چون راز دیگری همان را داشت، که با رازهای تصادفی هرگز پیش نمی‌آید. |

`stream`. هیچ شمارنده‌ای آدرس، مسیر، توکن یا کلیدی را نام نمی‌برد. هر که کاربر نبوده، به هر دلیلی، پاسخ مبدأ فریب را گرفته است، پس دلیل‌ها فقط برای اپراتورند:

| فیلد | معنا |
|---|---|
| `undecided`، `relayed`، `pending`، `sessions` | همین حالا: اتصال‌های درون دست‌دهی TLS یا خط درخواستشان، اتصال‌هایی که به مبدأ فریب رله می‌شوند، نشست‌هایی که اثباتشان پذیرفته شده و WireGuard هنوز رویشان احراز نشده، و نشست‌های برقرار. |
| `accepted`، `accept_failed`، `broken` | اتصال‌هایی که شنونده‌ها از سیستم گرفته‌اند، دفعه‌هایی که گرفتن اتصال شکست خورده، که نشانهٔ میزبانی است که توصیف‌گر فایل کم آورده، و اتصال‌هایی که پیش از تصمیم با خطایی غیر از بسته‌شدن قطع شدند، مثل reset وسط خط درخواست. |
| `handshake_failed`، `handshake_slow`، `handshake_displaced` | دست‌دهی‌های TLS که شکست خوردند، که در 10 ثانیه تمام نشدند، و که برای باز شدن جا در استخر تصمیم‌نگرفته‌ها بسته شدند. |
| `stranger_syntax`، `stranger_slow`، `stranger_closed`، `stranger_displaced`، `stranger_origin`، `stranger_proof` | اتصال‌هایی که «کاربر نیست» تشخیص داده شدند، بر پایهٔ دستهٔ دلیل: بایتی که نمی‌تواند جزء خط درخواست یک کاربر باشد یا خطی بلندتر از 4,096 بایت، خطی که در 10 ثانیه کامل نشد، طرفی که اول سمت خودش را بست، اتصالی که برای باز شدن جا بی‌درنگ درباره‌اش تصمیم گرفته شد، اتصالی که مبدأ فریبش پیش از کامل‌شدن خط درخواست چیزی فرستاد یا اتصال را بست، و خط درخواست کاملی که اثبات هیچ دستگاهی نیست. مسیر غلط، توکن غلط و دستگاه برداشته‌شده همه در همین آخری یکسان شمرده می‌شوند. |
| `refused_window`، `refused_floor`، `refused_seen`، `refused_cache_full` | اثبات‌های یک دستگاه که قاعدهٔ replay ردشان کرد: مهر زمانی بیش از 60 ثانیه دور از ساعت گره، مهر زمانی در کف یا زیر آن، توکنی که پیش‌تر پذیرفته شده، و هر اثباتی وقتی کش پر است. `refused_window` که بالا می‌رود نشانهٔ ساعت غلط روی یک دستگاه یا روی گره است. |
| `refused_limit`، `refused_no_replay` | اثبات‌هایی با مهر زمانی بالاتر از حدِ نوشته‌شده که نوشتنشان در 2 ثانیه تمام نشد یا 64 اثبات دیگر پیش از آن‌ها منتظر بودند، و اثبات‌هایی که وقتی رسیدند که گره هیچ اثباتی نمی‌پذیرفت. |
| `refused_pool`، `refused_pending`، `refused_device_rate`، `refused_source_rate` | اثبات‌هایی که یک حد ردشان کرد: `limits.sessions` شنونده پر است، دستگاه 2 نشست معلق دارد، یا سهم دستگاه (16 تا، بعد یکی در ثانیه) یا سهم مبدأ اتصال (`replay.per_source`) خرج شده. |
| `relays`، `relays_evicted`، `decoy_down` | اتصال‌هایی که به مبدأ فریب وصل و رله شدند، اتصال‌های رله‌شده‌ای که برای جا دادن به دیگری بسته شدند، و غریبه‌هایی که بی‌پاسخ بسته شدند چون مبدأ در دسترس نبود. تا وقتی `decoy_down` بالا می‌رود گره از مبدأ فریبش بازشناخته می‌شود: مبدأ را ببینید. |
| `proofs_accepted`، `proofs_waited`، `head_refused`، `established`، `establish_full` | اثبات‌های پذیرفته‌شده، اثبات‌هایی که منتظر نوشته‌شدن حد بالاتر ماندند، کاربرانی که سرآیند درخواستشان از حد گذشت یا upgrade به WebSocket نبود، نشست‌هایی که برقرار شدند، و نشست‌هایی که نتوانستند چون استخر نشست‌ها بعد از اثباتشان پر شده بود. |
| `handshakes`، `tunnel`، `queue_full`، `chunks_sent` | درون نشست‌ها: آغازگرهای دست‌دهی WireGuard بیش از سهم نشست (3 تا، بعد یکی در ثانیه)، دیتاگرام‌هایی که WireGuard بستهٔ دستگاهِ آن نشست ندانست، دیتاگرام‌هایی برای یک دستگاه که دور ریخته شدند چون صف ارسال اتصالش 256 تا داشت، و chunk هایی که گره فرستاد. `queue_full` که بالا می‌رود یعنی اتصالی کندتر از ترافیکی است که برایش می‌آید. |
| `ended_deadline`، `ended_idle`، `ended_packets`، `ended_displaced`، `ended_revoked`، `ended_closed`، `ended_invalid`، `ended_unserved` | نشست‌هایی که تمام شدند: هیچ بستهٔ WireGuard تا 10 ثانیه بعد از اثبات، هیچ chunk تا 300 ثانیه، تمام‌شدن شماره‌های chunk، نهمین نشست دستگاه، دستگاهی که به هر دلیلی قطع شد یا راز ترنسپورت یا کلید ترنسپورت گره‌ای که پیکربندی دیگر ندارد، اتصالی که بسته شد یا طرفی که نشست را بست، chunk ای که باز نشد یا فریمی که پروتکل اجازه نمی‌دهد، و ترنسپورتی که پیکربندی دیگر ندارد. |
| `upgrade_learned`، `upgrade_learn_failed` | چند بار فیلدهای سرآیند پاسخ upgrade از یک مبدأ فریب یاد گرفته شد، و چند بار این کار شکست خورد. تا وقتی آخرین تلاش شکست خورده، پاسخ upgrade فقط `Date` را از `upgrade_headers` دارد. شنونده‌ای که `upgrade_headers` آن هیچ فیلدی از مبدأ را نام نمی‌برد، که پیش‌فرض `ws` است، از مبدأ چیزی نمی‌پرسد و در هیچ‌کدام شمرده نمی‌شود. |
| `proxies`، `decoys`، `fronted` | همین حالا، روی شنونده‌های `ws` و `fronted`: اتصال‌های پراکسی‌های مورد اعتماد، درخواست‌هایی روی آن‌ها که در دست مبدأ فریب‌اند یا بدنه‌شان هنوز خوانده می‌شود و چیزی ثابت نکرده‌اند، و نشست‌های برقرار `fronted`. |
| `proxy_accepted`، `proxy_requests`، `proxy_unnamed`، `proxy_idle` | اتصال‌هایی که از یک پراکسی مورد اعتماد گرفته شدند، و درخواست‌هایی که روی آن‌ها خوانده شدند. `proxy_unnamed` آن درخواست‌هایی‌اند که، روی شنونده‌ای با `client_address_header`، آن سرآیند در آن‌ها هیچ مبدأیی را نام نبرد: خود پراکسی به‌جای بازدیدکننده شمرده شد، پس حدهای هر مبدأ برای همهٔ آن‌ها یک حد بود. وب‌سروری که این سرآیند را نمی‌گذارد اینجا دیده می‌شود، و `veilway doctor` همین دو شمارنده را می‌خواند. `proxy_idle` اتصال‌هایی‌اند که بعد از 300 ثانیه بدون درخواست بسته شدند. |
| `forwards`، `forwards_unframed`، `forwards_cut` | درخواست‌هایی که در مسیر پراکسی به مبدأ فریب داده شدند. `forwards_unframed` آن‌هایی‌اند که گره نتوانست پایانشان را تشخیص دهد: آن‌ها را به شکل بایت تا پایان پاسخ مبدأ رله کرد و بعد اتصال پراکسی را بست. `forwards_cut` اتصال‌هایی‌اند که بی‌درنگ بسته شدند چون یک مبدأ بیش از `limits.decoy_requests_per_source` درخواست منتظر داشت، یا همهٔ غریبه‌ها با هم بیش از نیمی از `limits.proxy_connections`. |
| `stranger_head`، `stranger_session`، `stranger_body`، `stranger_unestablished` | درخواست‌های مسیر پراکسی که به دلیلی که فقط همین مسیر دارد «کاربر نیست» تشخیص داده شدند: سرآیندی بلندتر از 16,384 بایت یا ناتمام بعد از 10 ثانیه، درخواست `fronted` ای که نشستی را با شماره‌ای خارج از نوبت یا هنگامی که درخواست دیگری از آن در راه است نام می‌برد، درخواستی که بدنه‌اش دیر رسید، باز نشد یا تکراری با بایت‌های دیگر بود، و درخواست آغازینی که هیچ بستهٔ WireGuard نشستش را برقرار نکرد. شمارنده‌های دیگر `stranger_` و `refused_` درخواست‌های این مسیر را هم می‌شمارند. |
| `polls`، `poll_repeats` | درخواست‌های `fronted` که پذیرفته شدند، با درخواست‌های آغازین، و تکرارهای آخرین درخواست پذیرفته‌شده که با پاسخ ذخیره‌شده جواب گرفتند. |
| `proxy_http10` | درخواست‌های پراکسی‌های مورد اعتماد که HTTP/1.0 بودند. هیچ‌کدام نمی‌تواند مال کاربر باشد: وب‌سروری که با گره HTTP/1.0 حرف بزند همهٔ کاربران را بیرون نگه می‌دارد، و باید به آن گفت با HTTP/1.1 حرف بزند. |
| `forwards_redialed`، `origin_dropped` | درخواست‌هایی که یک بار دیگر روی اتصال تازه به مبدأ فریب فرستاده شدند، چون مبدأ اتصالی را که از درخواست قبلی مانده بود بسته بود. و اتصال‌هایی به مبدأ فریب که گره رهایشان کرد چون مبدأ، بی آنکه درخواستی در دستش باشد، روی آن‌ها چیزی گفت یا آن‌ها را بست: هیچ چیز از این به پراکسی نمی‌رسد و اتصال پراکسی می‌ماند. |

`replay`. زمان‌ها ثانیهٔ یونیکس روی ساعت گره‌اند:

| فیلد | معنی |
|---|---|
| `ready` | وقتی هیچ اثباتی پذیرفته نمی‌شود `false` است: ریستی که هنوز معلوم نیست فایلش روی دیسک باشد. |
| `clock`، `floor`، `limit` | ساعت گره، زمانی که تا آن اثبات‌ها رد می‌شوند، و زمانی که بالاتر از آن اثبات پیش از نوشته شدن سقف بالاتر پذیرفته نمی‌شود. تا وقتی گره کار می‌کند `limit` بین 10 تا 20 ثانیه از `clock` جلوتر است. |
| `disk_limit` | بالاترین سقفی که ممکن است روی دیسک باشد، که شروعِ بعد از kill آن را کف خودش می‌گیرد. |
| `entries`، `capacity` | اثبات‌های درون cache، و `replay.cache` آن‌طور که گره با آن شروع شده. |
| `refusing_secs` | کف چند ثانیه از ساعت جلوتر است، به هر دلیلی. تا آن وقت اثبات‌های با ساعت درست رد می‌شوند. بعد از شروع یا ریست تا 80، که خودش می‌گذرد. |
| `floor_ahead`، `refused_floor_ahead` | آیا کف طوری از ساعت جلوتر است که هیچ شروعی توضیحش نمی‌دهد، یعنی بیش از 80 ثانیه یا بالا رفته هنگام کار گره، که همهٔ دستگاه‌ها را تا گذشتن ساعت از آن یا ریست حافظه رد می‌کند، و چند اثبات به این دلیل رد شده‌اند. |
| `writes`، `write_failures`، `slow_writes` | نوشتن‌های فایل replay که انجام شدند، که شکست خوردند، و که بیش از 2 ثانیه طول کشیدند. تا وقتی `write_failures` بالا می‌رود گره اثبات تازه‌ای نمی‌پذیرد. |
| `limit_lowered`، `resets` | چند بار گره سقف خودش را بعد از ساعتی که جلو رفته بود پایین آورد، و چند بار حافظه ریست شد. |

### `GET /v1/sessions`

`{"sessions": [...]}`، برای هر دستگاهِ دارای نشست زنده روی یک ورودی یک مورد: `user`، `device`، `public_key`، `inbound`، `transport` (`udp`، `ws`، `udp-obfs`، `tls` یا `fronted`، به همان نامی که پیکربندی دارد، پس `ws` روی ورودی `veilway` همان `ws` بومی است؛ وقتی ترنسپورتی که دستگاه با آن آمده دیگر نیست، یا نشست `udp-obfs`، `tls`، `ws` یا `fronted` آن تمام شده، `null`)، `handshake_age_secs`، `flows` (فلوهای دستگاه روی همهٔ ورودی‌هایش)، `selected_exit` (خروجی‌ای که دستگاه روی کانال کنترل انتخاب کرده؛ وقتی انتخابی نکرده و از خروجی کاربرش می‌رود `null`)، `control_connections` (اتصال‌های کنترل احرازشده‌اش) و `mtu` (MTU ای که دستگاه تعیین کرده؛ وقتی تعیین نکرده و تونلش MTU ورودی را دارد `null`).

آدرسی که دستگاه از آن وصل می‌شود جزو نشست نیست. `log.destinations` هر چه بگوید، این آدرس هرگز در پاسخ نمی‌آید.

### `GET /v1/exits`

`{"exits": [...]}`.

| فیلد | معنی |
|---|---|
| `tag`، `name` | اگر پیکربندی نامی ندهد `name` همان تگ است. |
| `backend` | `netstack`، `l3`، `block` یا `chain`. |
| `outbound` | تگ outbound بک‌اند `netstack`، وگرنه `null`. |
| `udp` | تا آنجا که گره می‌داند، آیا پروکسی SOCKS5 این خروجی UDP را رله می‌کند. برای خروجی بدون پروکسی SOCKS5 `null`. |
| `udp_down_secs` | ثانیه‌های گذشته از آخرین باری که پروکسی رله‌کردن UDP را رد کرد. گره هر یک دقیقه دوباره امتحان می‌کند. مگر وقتی `udp` برابر `false` باشد `null` است. |
| `udp_flips` | چند بار پروکسی بین رله‌کردن UDP و نکردن جابه‌جا شد. |
| `interface_up` | آیا رابط بک‌اند `l3` بالا است. تا وقتی `false` است، ترافیکی که به این خروجی مسیریابی شده پاسخ «غیرقابل دسترس» می‌گیرد و گره دوباره برای برپا کردن رابط تلاش می‌کند: 2 ثانیه پس از افتادن، بعد هر بار با دو برابر فاصلهٔ قبلی، حداکثر هر یک دقیقه یک بار. برای هر بک‌اند دیگر `null`. |
| `interface_down_secs` | ثانیه‌های گذشته از افتادن رابط. مگر وقتی `interface_up` برابر `false` باشد `null` است. |
| `interface_flips` | چند بار رابط بین بالا و پایین جابه‌جا شد. |
| `links` | تگ لینک‌های گرهِ یک بک‌اند `chain` که `/v1/links` دربارهٔ آن‌ها گزارش می‌دهد. برای هر بک‌اند دیگر خالی است. |
| `link_up` | آیا یکی از آن لینک‌ها بالا است. تا وقتی هیچ‌کدام بالا نباشد، ترافیکی که به این خروجی مسیریابی شده پاسخ «غیرقابل دسترس» می‌گیرد و راه دیگری ندارد. برای هر بک‌اند دیگر `null`. |
| `latency_ms`، `measured_at` | مثل outbound در `/v1/stats`، برای outbound بک‌اند `netstack`. وگرنه `null`. |
| `traffic` | شمارنده‌ها، مثل کاربر. |

### `GET /v1/inbounds`

`{"inbounds": [...], "public_addresses": [...]}`. `public_addresses` همان فهرست `GET /v1/status` است. برای هر ورودی پیکربندی در حال اجرا یک مورد هست. هیچ کلید خصوصی جزو آن نیست.

| فیلد | معنی |
|---|---|
| `tag` | تگ ورودی. |
| `kind` | `wireguard` یا `veilway`، یعنی `type` ورودی. |
| `public_key` | کلید عمومی WireGuard ورودی. |
| `transport_public_key` | نیمهٔ عمومی کلید ترنسپورت گره که پروفایل با خود دارد. برای ورودی بدون `transport_keys` برابر `null` است. |
| `transports` | برای هر ترنسپورت یک `{"transport", "rating"}`، به ترتیب پیکربندی. `transport` یکی از `udp`، `ws`، `udp-obfs`، `tls` یا `fronted` است. `rating` آن چیزی است که سانسورچی از اتصال یک پروفایل می‌تواند ببیند: `protected`، `detectable` یا `unsafe`. در این نسخه همهٔ ترنسپورت‌ها `detectable` رتبه می‌گیرند. |

### `GET /v1/links`

`{"links": [...]}`، برای هر [لینک گرهِ](../../protocol/node-links/) فعال یک مورد. هیچ کلید و رازی جزو آن نیست.

| فیلد | معنی |
|---|---|
| `tag`، `id` | تگ لینک و شناسهٔ آن (22 نویسه base64url). |
| `half` | `entry` وقتی این گره کاربران را دارد و بسته‌هایشان را از راه یک خروجی با بک‌اند `chain` به لینک می‌فرستد. `exit` وقتی آنچه از لینک می‌رسد از این گره بیرون می‌رود. |
| `role` | `listener` وقتی لینک به یک ورودی این گره وصل می‌شود، `dialler` وقتی این گره به گره دیگر وصل می‌شود. |
| `state` | `up` (یک handshake وایرگارد در 180 ثانیهٔ گذشته کامل شده)، `connecting`، `unreachable` (هیچ کاندیدای گرهٔ دیگر پاسخ نمی‌دهد)، `refused` (گرهٔ دیگر پاسخ می‌دهد و اثبات را نمی‌پذیرد) یا `ended` (24 ساعت handshake نبوده، یا این گره لینک را به‌خاطر سهمیه یا انقضا قطع کرده). گره‌ای که وصل می‌شود از `ended` به بعد روزی یک بار دوباره امتحان می‌کند. |
| `state_secs`، `state_flips` | ثانیه‌هایی که لینک در `state` بوده، و چند بار `state` عوض شده. |
| `handshake_secs` | ثانیه‌های گذشته از آخرین handshake کامل تونل لینک. بدون نشست `null`. |
| `transport`، `transport_index`، `candidate_index` | روی گرهٔ وصل‌شونده: ترنسپورتی که روی آن است، و جای آن ترنسپورت و کاندیدایش در فهرست گرهٔ دیگر، از 0. روی گرهٔ پذیرنده همه `null` هستند. |
| `size_warning` | `true` وقتی سیستم در 600 ثانیهٔ گذشته یک بستهٔ بیرونی لینک را به‌خاطر اندازه رد کرده، که نشان می‌دهد `mtu` لینک برای مسیر زیاد است. هر کسی روی مسیر می‌تواند چنین گزارشی را جعل کند، پس فقط هشدار می‌دهد. |
| `denied` | روی نیمهٔ خروج: چرا این گره لینک را قطع کرده (`disabled`، `expired` یا `quota`). برای لینکی که اجازهٔ کار دارد `null`. |
| `exit` | روی نیمهٔ ورود: خروجی با بک‌اند `chain` که لینک پشت آن است. |
| `flows` | فلوهایی که لینک حمل می‌کند. |
| `dropped` | بسته‌هایی که از لینک بیرون آمدند و حمل نشدند. |
| `traffic` | بسته‌های داخلی. up آنچه این گره به لینک فرستاد، down آنچه از آن گرفت. |

## رویدادها

`GET /v1/events` یک جریان Server-Sent Events است (`text/event-stream`). هر رویداد یک `id` افزایشی، نام `event` و یک سند JSON به‌عنوان `data` دارد.

| رویداد | داده |
|---|---|
| `config_applied` | `generation`، `revision`، `diff`. یک reload با `SIGHUP` یا یک apply. |
| `config_refused` | `stage` (`validate` یا `prepare`) و `errors` (تعدادشان). reload یا applyای که پیکربندی در حال اجرا را سر جایش گذاشت. |
| `user_cut_off` | `user` و `reason`: `disabled`، `expired`، `quota` یا `removed`. |
| `user_restored` | `user`. |
| `usage_reset` | `user` و `totals` (اینکه شمارنده‌های طول عمر هم صفر شدند یا نه). برای هر ریست مصرف فرستاده می‌شود. |
| `exit_udp_changed` | `exit` و `udp` (وضعیت تازه). |
| `stats` | عکس لحظه‌ای `/v1/stats`، هر ثانیه. فقط وقتی ساخته می‌شود که کسی جریان را می‌خواند. |
| `lagged` | `missed`. `id` ندارد. |

```
event: user_cut_off
id: 42
data: {"user":"alice","reason":"quota"}
```

- **خواننده‌های کند.** گره هرگز بی‌حد بافر نمی‌کند. خواننده‌ای که عقب بیفتد قدیمی‌ترین رویدادها را از دست می‌دهد و `lagged` با تعداد رویدادهای ازدست‌رفته می‌گیرد که از فاصله‌های بین idها شمرده می‌شود. این هم رویدادهایی را شامل می‌شود که خود گره نتوانست نگه دارد و هم رویدادهایی که این خواننده برایشان کند بود. `lagged` درست پیش از رویداد بعدیِ نگه‌داشته‌شده می‌آید.
- **نگه‌داشتن اتصال.** هر 15 ثانیه یک خط توضیح (`: keepalive`) فرستاده می‌شود.
- **اتصال کند.** اتصالی که خواننده‌اش 30 ثانیه چیزی برنمی‌دارد در حالی که گره چیزی برای فرستادن دارد بسته می‌شود.
- **بعد از شکاف.** بازپخش وجود ندارد. کلاینتی که دوباره وصل می‌شود باید وضعیت را از مسیرها دوباره بخواند.

## محدودیت‌ها

| محدودیت | مقدار |
|---|---|
| بدنهٔ درخواست | 4 MiB |
| خط درخواست و هدرها روی هم | 16 KiB، حداکثر 64 هدر |
| اتصال همزمان | 64. اتصال بعدی `503 too_many_connections` می‌گیرد و بسته می‌شود. |
| جریان رویداد همزمان | 32، از میان همان اتصال‌ها |
| زمان یک درخواست، از اولین بایت تا پاسخ | 30 ثانیه. همین مدت یک اتصال می‌تواند منتظر درخواست بعدی بماند. |
| سند پیکربندی که همزمان بررسی می‌شود | 2. سند سوم در مهلت درخواستش منتظر نوبت می‌ماند. |
| رویدادهای نگه‌داشته برای خواننده کند | 256 |

بدنهٔ درخواست ردشده تا چهار برابر حد خوانده و دور ریخته می‌شود، تا کلاینتی که هنوز می‌فرستد بتواند دلیل رد شدن را بخواند. بعد از آن اتصال قطع می‌شود.

## کلاینت TypeScript

`@veilway/sdk` (نسخهٔ `0.2.2-alpha`، [صفحهٔ آن](../../sdk/typescript/)) یک کلاینت تایپ‌دار است که از سند OpenAPI ساخته می‌شود. وابستگی زمان اجرا ندارد. یک تابع `fetch` و یک آدرس پایه می‌گیرد، پس راه رسیدن به سوکت یونیکس با شماست. مثال زیر از `undici` استفاده می‌کند:

```ts
import {Agent, fetch as undiciFetch} from "undici";
import {Client, VeilwayError, type Fetch} from "@veilway/sdk";

const dispatcher = new Agent({connect: {socketPath: "/srv/veilway/veilway.sock"}});
const fetch: Fetch = (url, init) => undiciFetch(url, {...init, dispatcher}) as unknown as ReturnType<Fetch>;
const client = new Client(fetch, "http://veilway");
const running = await client.getConfig();
try {
	await client.applyConfig({...running.document, log: {level: "debug"}}, running.revision);
} catch (e) {
	if (e instanceof VeilwayError) console.log(e.status, e.code, e.details);
}
for await (const event of client.events()) {
	if (event.event === "user_cut_off") console.log(event.data.user, event.data.reason);
}
```

متدها: `status`، `getConfig`، `validateConfig`، `diffConfig`، `applyConfig`، `listUsers`، `getUser`، `resetUsage`، `resetReplay`، `stats`، `listSessions`، `listExits`، `listInbounds`، `listLinks` و `events`. هر شکستی به شکل `VeilwayError` با `status`، `code`، `message` و `details` پرتاب می‌شود. `resetUsage(name, {totals: true})` مصرف یک کاربر را ریست می‌کند و کاربر را برمی‌گرداند. `resetReplay()` حافظهٔ replay را ریست می‌کند و آن را برمی‌گرداند؛ اول هزینه‌اش را زیر `POST /v1/replay/reset` بخوانید. `events` وقتی گره جریان را ببندد یا signal لغو شود تمام می‌شود و رویدادهای `lagged` را هم می‌دهد.

## هنوز ساخته نشده

- دسترسی از راه دور: شنونده TCP، توکن و TLS دوطرفه. فعلاً سوکت تنها راه ورود است.
- مسیر لاگ‌ها.
- قطع دستی یک نشست.
- تغییر یک کاربر، ورودی یا لینک به‌تنهایی. نوشتن‌ها فقط یک پیکربندی کامل (`PUT /v1/config`)، ریست مصرف و ریست replay هستند.
